Information Retrieval con Embeddings & LLM

Del emparejamiento léxico tradicional (TF-IDF / BM25) al espacio semántico vectorial y RAG

TF-IDF / BM25 (Léxico) Dense Embeddings (Semántico) RAG (Retrieval + Generación) ChromaDB (Vector Engine)
"En la clase 2 construimos motores de búsqueda léxica con TF-IDF, matrices término-documento e índices invertidos. Hoy damos el salto cualitativo: ¿qué pasa cuando el ciudadano o proveedor no utiliza exactamente las mismas palabras que redactó la entidad pública en el pliego de condiciones?"

El Límite del Modelo Léxico

TF-IDF premia la coincidencia exacta de tokens. Si el pliego dice «adquisición de soluciones ofimáticas» y la consulta es «licencias de software de oficina», el producto punto léxico es cero. Hay un abismo de vocabulario.

La Promesa del Modelo Denso

Los modelos basados en Transformers proyectan el lenguaje a espacios métricos continuos de dimensión fija (d = 384, 768). La relevancia deja de ser un conteo superficial de palabras y se convierte en proximidad geométrica en un hiperespacio.

De la Búsqueda Léxica (TF-IDF) a la Búsqueda Densa (Dense Retrieval)

Comparativa de Fundamentos Matemáticos

Criterio TF-IDF / BM25 (Sparse) Dense Embeddings (Bi-Encoders)
Vector Disperso: dimensión |V| ∼ 50.000 (casi todos ceros) Denso: dimensión fija d ∈ [384, 1536] (valores continuos)
Sinonimia Ortogonalidad estricta (u · v = 0) Proximidad semántica (cos(θ) ≈ 1.0)
Contexto Bolsa de palabras; ignora orden sintáctico Atención contextual; comprende negaciones y matices
Indexación Inverted Index (Posting Lists) Grafo de vecinos más cercanos aproximados (HNSW)

Demostración en Contratación Estatal

# Caso Real: Dos textos con exactamente el mismo sentido legal doc = "Suministro de programas ofimáticos y suites de productividad" query = "Compra de licencias de software para oficina" # 1. Enfoque Léxico (TF-IDF / BM25): # Tokens compartidos = 0 -> Similitud léxica = 0.0 Resultado: Documento descartado (Falso Negativo crítico) # 2. Resultado: Requisito técnico encontrado exitosamente

Memoria Paramétrica vs. No Paramétrica

  • Memoria Paramétrica (Pesos del LLM): Estática, congelada en la fecha de corte del modelo. No conoce la licitación publicada ayer en SECOP II. Alucina plazos y leyes inventadas si no sabe la respuesta.
  • Memoria No Paramétrica (Base Vectorial Externa): Dinámica, actualizable en segundos sin reentrenamiento, privada, auditable y con trazabilidad exacta a la fuente.

¿Por qué no meter todo el PDF en el Context Window?

  • Efecto "Lost in the Middle": En documentos de 200+ páginas (100k+ tokens), la atención del Transformer se degrada severamente en el centro del texto.
  • Costo y Latencia: Pasar 150 páginas en cada turno de conversación eleva el costo financiero y genera latencias de 20 a 40 segundos por respuesta.
  • Principio RAG: Recuperar únicamente los k fragmentos más densamente relevantes (k = 3), reduciendo el contexto a menos de 1.500 tokens.

Bases de Datos Vectoriales: ¿Por qué ChromaDB?

1. El Problema de Escala en IR

En una base relacional tradicional (SQL), buscar los vectores más cercanos a una consulta requiere un cálculo de distancia euclidiana o coseno fila por fila: O(N · D).

Con miles de pliegos y millones de chunks, una búsqueda lineal (KNN exacto) es prohibitiva en tiempo real. Se requiere ANN (Approximate Nearest Neighbors).

2. El Algoritmo HNSW

Hierarchical Navigable Small World: el estándar de oro en indexación vectorial.

Construye un grafo multicapa (similar a una Skip List multidimensional). La capa superior da "saltos largos" en el hiperespacio, y las capas inferiores refinan la búsqueda localmente. Complejidad de consulta: O(log N).

3. Arquitectura ChromaDB

Motor vectorial open-source diseñado para IA y desarrollo ágil:

  • Colecciones: Espacios vectoriales aislados (multi-tenancy por licitación).
  • Embedding Functions desacopladas: Permite pasar texto crudo o vectores precalculados.
  • Almacenamiento híbrido: SQLite para metadatos + biblioteca hnswlib en C++ para índices vectoriales.
"ChromaDB abstrae la matemática pesada de indexación HNSW detrás de una API simple de tres verbos: add(), query() y delete()."

Las Dos Fases Operativas

INDEX TIME (Carga e Ingesta del Pliego) collection = client.get_or_create_collection( name="IDARTES-2026", metadata={"hnsw:space": "cosine"} # Espacio métrico ) collection.add( documents=[chunk_1, chunk_2, ...], metadatas=[{"fuente": "pliego.pdf", "page": 12}, ...], ids=["c1", "c2", ...] ) # 2. QUERY TIME (Recuperación Semántica) results = collection.query( query_texts=["licencias de diseño gráfico"], n_results=3, where={"page": {"$gt": 5}} # ¡Filtrado híbrido con metadatos! )

Métricas de Distancia en el Hiperespacio

Coseno (Angular) — Recomendada para Texto

dcos(u, v) = 1 − (u · v) / (||u||2 ||v||2). Mide el ángulo entre vectores. Es invariante a la longitud del fragmento de texto (compara orientación temática pura).

Distancia Euclidiana L2

dL2(u, v) = ||u − v||2. Mide la distancia geométrica directa en línea recta. Cuando los embeddings están normalizados (||u||2 = 1), L2 es monótona y directamente equivalente al Coseno.

Producto Punto Interno (IP)

dIP(u, v) = 1 − (u · v). La métrica más rápida de calcular a nivel de hardware cuando todos los vectores están previamente normalizados.

Fase 0 — Smoke Test: Fundamentos Vectoriales

Objetivo Didáctico

Verificar que el entorno vectorial está correctamente configurado en local antes de tocar un solo PDF o llamar un modelo generativo.

  • ChromaDB efímero: Operaciones en memoria para validar la instalación sin efectos secundarios en disco.
  • Embeddings multilingües: Uso de paraphrase-multilingual-MiniLM-L12-v2 optimizado para español técnico institucional.
  • Distancia semántica: Comprobación de que la distancia L2/coseno correlaciona con la similitud de conceptos (licencias vs pliego).
# fase0_smoke_test.py — Verificación en 40 líneas ef = SentenceTransformerEmbeddingFunction( model_name="paraphrase-multilingual-MiniLM-L12-v2" ) client = chromadb.Client() # En memoria col = client.create_collection("prueba", embedding_function=ef) col.add( documents=["Pliego condiciones técnicas software", ...], metadatas=[{"fuente": "pliego_001.pdf"}], ids=["d1", "d2"] ) res = col.query(query_texts=["licencias"], n_results=2) # Salida: distancia semántica calculada en milisegundos

Fase 1 — Motor RAG sobre Pliegos (Retrieval Puro)

Diseño & Decisiones de Ingeniería

  • Sin LLM en el loop: Fase 1 es retrieval determinista. No genera texto; recupera fragmentos con citas exactas (página, fuente, score).
  • Aislamiento por proceso: Cada licitación tiene su propia colección vectorial persistente en chroma_db/<licitacion>/. Previene contaminación cruzada de pliegos.
  • Chunking consciente: RecursiveCharacterTextSplitter (1000 caracteres, 200 de solape) preserva párrafos legales y listas técnicas.
  • Carga trazable: PyPDFLoader extrae página por página, almacenando metadata["page"] para auditoría posterior.
"Si el retrieval falla o alucina en la Fase 1, ningún LLM avanzado en la Fase 3 podrá salvar la respuesta."
class PliegoRAG: def __init__(self, licitacion: str): self.vectorstore = Chroma( collection_name=licitacion, persist_directory=f"chroma_db/{licitacion}", embedding_function=adaptador_embeddings ) def esta_indexada(self) -> bool: # API pública sin depender de _collection interna return len(self.vectorstore.get()["ids"]) > 0 def consultar_pliego(self, query: str, k=3) -> list[dict]: return self.vectorstore.similarity_search_with_score( query, k=k )

Fase 2 — Tooling de Datos Abiertos (API SECOP II)

De la API SODA al Conocimiento Tabular

Consumo del dataset jbjy-vk9h en datos.gov.co mediante cliente oficial sodapy.

  • Filtro SoQL: Cláusulas where eficientes por objeto_del_contrato y codigo_de_categoria_principal (UNSPSC).
  • Normalización con Pandas: Conversión segura de valor_del_contrato a punto flotante (manejando nulos y texto sucio).
  • Agregación analítica: Agrupación por NIT y Razón Social; cálculo de contratos adjudicados y total ejecutado.
  • Salida para LLM: Generación directa de tabla Markdown con formato de moneda colombiana ($ 1.234.567).
# fase2_secop_tools.py — Consulta y agregación termino_seguro = termino_clave.replace("'", "") where = f"objeto_del_contrato like '%{termino_seguro}%'" if unspsc: where += f" and codigo_de_categoria_principal = '{unspsc}'" filas = cliente.get("jbjy-vk9h", where=where, limit=100) df = pd.DataFrame(filas) resumen = ( df.groupby(["proveedor_adjudicado", "documento_proveedor"])["valor"] .agg(contratos="count", total_ejecutado="sum") .sort_values("total_ejecutado", ascending=False) )

Fase 3 — Agente Orquestador (LangChain 1.x + NVIDIA)

Orquestación con Tool Calling Autónomo

Construcción mediante create_agent (LangGraph runtime) con dos herramientas declaradas con decorador @tool:

  • tool_rag_pliegos(licitacion, pregunta): Lee requisitos técnicos.
  • tool_secop_proveedores(termino, depto, unspsc): Consulta mercado.

Control de Inferencia & Resiliencia:

  • Thinking Mode Desactivado: enable_thinking: False en Nemotron evita monólogos de razonamiento largos y garantiza latencias < 5s.
  • Límite de Recursión: RECURSION_LIMIT = 12 evita loops infinitos en casos de herramientas ambiguas.
  • Memoria de Sesión: MemorySaver con thread_id para mantener contexto multi-turno.
@tool def tool_rag_pliegos(licitacion: str, pregunta: str) -> str: """Consulta condiciones y lotes de un pliego PDF.""" rag = PliegoRAG(licitacion) if not rag.esta_indexada(): rag.indexar(...) return formatear_resultados(rag.consultar_pliego(pregunta)) llm = ChatNVIDIA( model="nvidia/nemotron-3.5-lightning-30b-a3b", temperature=0, model_kwargs={"chat_template_kwargs": {"enable_thinking": False}} ) agente = create_agent( model=llm, tools=[tool_rag_pliegos, tool_secop_proveedores], system_prompt="Eres consultor experto en contratación...", checkpointer=MemorySaver() )

Brecha del Laboratorio

ChromaDB en SQLite local no soporta concurrencia, reinicia en cada pod y no escala a gigabytes de pliegos.

Solución Cloud: Base vectorial administrada con índices HNSW, sharding y particionado multi-tenant nativo.

Bloqueo de Ingestión

Indexar 300 páginas de PDFs durante una petición HTTP congela el proceso por 90 segundos.

Solución Cloud: Ingesta asíncrona con cola de mensajes (Celery/Cloud Tasks), workers dedicados y webhooks de notificación.

PDFs Escaneados y Tablas

PyPDFLoader pierde tablas complejas, anexos presupuestales y páginas escaneadas sin texto digital.

Solución Cloud: Pipeline con Docling/Unstructured, extracción de tablas Markdown y OCR en fallback (Tesseract/Surya).

Producción II — Resiliencia, Guardrails & Evaluación Continua

La Tríada de Evaluación RAG (LLM-as-a-Judge)

En contratación estatal una respuesta incorrecta implica riesgo jurídico. Se debe medir automáticamente con Ragas o DeepEval en CI/CD:

Dimensión Qué mide Objetivo Prod
Faithfulness ¿La respuesta se sustenta 100% en el pliego? > 0.95 (cero alucinación)
Answer Relevance ¿Responde directamente la duda del usuario? > 0.90
Context Recall ¿El RAG recuperó todos los lotes/requisitos? > 0.92

Guardrails & Robustez Operativa

🛡️ Sanitización Estricta de Queries SoQL

Prohibir concatenación cruda. Usar parámetros validados con Pydantic y listas blancas de departamentos y códigos UNSPSC.

⚡ Caché en Dos Niveles (Redis)

Caché TTL (6 horas) sobre la API de SECOP II. Evita rate limits de datos.gov.co y reduce la latencia de 3.2s a 15ms en consultas repetidas.

🔄 Fallback de Modelos (Circuit Breaker)

Si la API de NVIDIA tiene timeout o error 429, conmutar automáticamente a Azure OpenAI o endpoint vLLM self-hosted.

Producción III — Observabilidad, FinOps & Cumplimiento

1. Observabilidad (LangSmith / OTel)

Trazabilidad total de cada ejecución:

  • Latencia por nodo (RAG vs LLM vs API SODA).
  • Captura de tool calls fallidos o parámetros mal formados.
  • Monitoreo de drift semántico en las preguntas ciudadanas.
  • Alarmas P99 ante degradación de la API de datos abiertos.

2. FinOps & Arquitectura Jerárquica

Optimización drástica de costos de cómputo:

  • Small Language Models (SLM 8B): Enrutamiento rápido y extracción de entidades (UNSPSC, lotes).
  • Large LLM (70B / Nemotron): Síntesis final con contexto consolidado.
  • Caché Semántico (GPTCache): Respuestas precalculadas ante preguntas idénticas de proponentes.

3. Cumplimiento Legal (Ley 1581)

Gobernanza de datos de contratación pública:

  • Anonimización de PII: Enmascaramiento de cédulas de representantes de personas naturales antes de enviar al LLM externo.
  • Trazabilidad Legal: Cita obligatoria con hash criptográfico del PDF y número de página verificable.
  • Gestión de Secretos: Vault o AWS KMS; rotación automática de tokens API.
